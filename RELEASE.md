Автор: INew

## v1.0.6 — отдельное исправление чтения аудита DEV

Windows Manager после подтверждённого отсутствия `sudo` предлагает отдельный просмотр
плана. Agent читает `platform-operator` сам и добавляет только `sudo` на точном
`sys/audit`, сохраняя остальные capability-блоки. Произвольные пути/HCL от клиента
не принимаются. PROD запрещён этой операцией.

План `operator-audit-read-repair-v1` связан с SHA-256 исходного и ожидаемого HCL,
действует пять минут. Необходимо точное подтверждение `DEV` и две разные Unseal-доли.
Перед единственной записью обязательны повторная проверка policy и durable Raft-снимок;
затем контрольное чтение policy и `sys/audit` с токеном оператора, отзыв временного root.
Потеря ответа на запись вызывает проверку результата, а не повтор POST. При
неподтверждённом отзыве блокируются новые повышения. Перезапуск не восстанавливает
OTP/доли/root из файла: используются прежние правила аварийной диагностики по operation ID.

Поддерживается ограниченный HCL из `path`/`capabilities` с комментариями. `deny` на
совпадающем пути, неоднозначные блоки, дополнительные ограничения и неподдерживаемый
синтаксис закрывают операцию без изменения policy. ACL API не имеет CAS: на время
применения исключите параллельное внешнее редактирование `platform-operator`.

Обновляйте только DEV после проверки комплекта. Установщик сохраняет существующую
привязку устройств; удалять state или сертификаты не требуется. После исправления
нажмите «Проверить платформу»: эта операция не создаёт `apps-kv` и не объявляет
проект или весь контур готовым.

## v1.0.5 — работа с IP-привязкой оператора

- Исходный IP определяется только после проверки сертификата устройства и только от непосредственного локального прокси 127.0.0.1.
- Из X-Forwarded-For берётся последнее значение, которое штатный nginx добавляет через $proxy_add_x_forwarded_for. Клиентская цепочка слева не используется и не пересылается.
- В каждый запрос к OpenBao передаётся один проверенный адрес; параллельные запросы не используют общий изменяемый заголовок.
- После успешного lookup-self Agent дополнительно сопоставляет IP с bound_cidrs. Чужой IP, отсутствие доверенного адреса или некорректное ограничение блокируют IP-bound токен.
- Сохраняются проверки mTLS, Userpass, root, entity, policy, service, числа использований, TTL и отзыва. IP-ограничения пользователя не отключаются.
- Метки TAR и имени комплекта формируются в UTC, без прежнего трёхчасового сдвига.

На изолированном OpenBao 2.6.1 проверены Userpass + TOTP со строгой IP-привязкой, разрешённый IP, отказ с чужого IP и через loopback без исходного адреса, а также отзыв токена. DEV и PROD проходят отдельные сценарии. Проверки не подтверждают готовность конкретного Ubuntu-сервера.

### Проверка IP-привязки перед обновлением

1. Сначала работайте только с DEV. Сохраните текущие параметры установки; существующие CA и привязки удалять не нужно.
2. Администратор проверяет активный listener OpenBao и конфигурацию nginx, включая глобальные real_ip-настройки. Внешний клиент не должен иметь возможность изменить $remote_addr.
3. Штатный nginx Agent дописывает реальный адрес клиента справа. Если есть внешний балансировщик или другой прокси, его доверие необходимо проверить отдельно; нельзя вслепую менять выбор адреса на первый элемент заголовка.
4. OpenBao должен принимать X-Forwarded-For только от проверенного прокси. Для проверенной схемы с nginx и Agent на том же сервере применимы x_forwarded_for_authorized_addrs = ["127.0.0.1/32"] и x_forwarded_for_hop_skips = 0. Это не команда для замены рабочего конфига: параметры отказа при отсутствии заголовка и существующие локальные клиенты проверяются отдельно. Не расширяйте доверие до внешних сетей.
5. Установите проверенный Linux-комплект и убедитесь, что /api/v1/version показывает 1.0.5. Ответ health проверяет готовность процесса, а не права оператора или IP-маршрут.
6. Откройте исправленную локальную Windows-сборку, выполните новый вход DEV с TOTP, затем «Проверить Agent» и «Проверить вход оператора». При отказе не повторяйте вход по кругу: проверьте маршрут исходного IP, TTL и права.
7. После успешной проверки оператора проверьте первый проект DEV. Только затем повторите проверку и установку отдельно для PROD.

Установщик не изменяет конфигурацию OpenBao, не отключает IP-привязку и не перезапускает OpenBao. Доступ недоверенных локальных процессов к listener остаётся отдельной границей доверия.

Официальное описание: [TCP listener OpenBao](https://openbao.org/docs/configuration/listener/tcp/).

## v1.0.4 — совместимость с OpenBao 2.6.1

- Исправлена проверка штатных Userpass-токенов, включая identity policies; удалено требование несуществующего поля `meta.environment_id`.
- Установщик разрешает orphan service-токены Userpass с сохранением остальных защитных проверок.
- Состояние хранилища читается через `sys/seal-status`, audit — из штатного `data`, MFA — через применимые login-enforcement и типы методов.
- Версия бинарника формируется из версии выпуска и должна соответствовать manifest.

На изолированном OpenBao 2.6.1 проверены MFA, проверка и отзыв оператора, чтение состояния, создание проекта и выдача AppRole-доступа в сценариях DEV/PROD. Это не заменяет проверку systemd, Nginx, TLS/mTLS и действующих policy на вашем Ubuntu-сервере.

Обновляйте сначала DEV, затем проверяйте вход и первый проект. Только после успешной проверки переходите к PROD. Установщик сохраняет существующие device CA и состояние привязки, но заново спрашивает параметры среды: используйте действующие значения и не удаляйте конфигурацию или state для повторной установки.

## Проверка комплекта

После распаковки Release asset выполните:

```bash
bash ./verify-release.sh
bash -n ./install.sh
```

Успешная проверка завершается строкой `release_valid sha256=<хеш>`.

## Службы и файлы

Для среды `<env>` используются:

- служба `inew-openbao-control-agent@<env>.service`;
- конфигурация `/etc/inew-openbao-control-agent/<env>/agent.json`;
- состояние `/var/lib/inew-openbao-control-agent/<env>`;
- аудит `/var/log/inew-openbao-control-agent/<env>`;
- резервные копии Agent `/var/backups/inew-openbao-control-agent/<env>`;
- Nginx `/etc/nginx/conf.d/inew-openbao-control-agent-<env>.conf`;
- версии `/opt/inew-openbao-control-agent/releases/<version>` и независимая ссылка `current-<env>`.

Каталог распаковки Release asset не является каталогом установки. Допустимо скачать и распаковать архив в созданный через `mktemp -d` временный каталог: после успешного `sudo ./install.sh` служба использует только постоянные пути выше. Для DEV точкой запуска является `/opt/inew-openbao-control-agent/current-dev/inew-openbao-control-agent`, для PROD — `/opt/inew-openbao-control-agent/current-prod/inew-openbao-control-agent`.

Проверка фактических путей после установки DEV:

```bash
readlink -f /opt/inew-openbao-control-agent/current-dev
systemctl cat inew-openbao-control-agent@dev.service
systemctl is-enabled inew-openbao-control-agent@dev.service
systemctl is-active inew-openbao-control-agent@dev.service
```

Первая команда должна показать каталог `/opt/inew-openbao-control-agent/releases/<version>`, а `ExecStart` — путь через `current-dev`. Для PROD замените `dev` на `prod`.

Быстрая диагностика:

```bash
sudo systemctl status inew-openbao-control-agent@dev.service
sudo journalctl -u inew-openbao-control-agent@dev.service --since today
sudo nginx -t
curl --fail http://127.0.0.1:9120/api/v1/health
```

Замените `dev` и порт на значения нужной среды. Не отправляйте журнал в публичный issue без обезличивания.

## Новый одноразовый код привязки

На уже установленной среде временно остановите службу, создайте код от имени её системного пользователя и сразу запустите службу:

```bash
sudo systemctl stop inew-openbao-control-agent@dev.service
sudo -u inew-openbao-agent-dev /opt/inew-openbao-control-agent/current-dev/inew-openbao-control-agent \
  --config /etc/inew-openbao-control-agent/dev/agent.json --create-pairing
sudo systemctl start inew-openbao-control-agent@dev.service
```

Код вводится в OpenBao Manager и не должен сохраняться в тикете, истории команд или общем чате.

## Откат

При ошибке установщик автоматически восстанавливает заменённые файлы и прежнее состояние службы. Путь к резервной копии выводится после успешной установки. Системный пользователь и созданные каталоги намеренно не удаляются автоматически: это исключает потерю состояния при ошибочном определении принадлежности файлов.

Для ручного отката остановите службу, восстановите только нужные файлы из указанного `install-<timestamp>-<env>`, верните прежнюю ссылку `current`, затем выполните:

```bash
sudo systemctl daemon-reload
sudo nginx -t
sudo systemctl restart inew-openbao-control-agent@dev.service
sudo systemctl reload nginx
```

## Правила выпуска

1. Публичный Git ZIP содержит только текстовые файлы репозитория и не содержит `release/`.
2. GitHub Release asset содержит те же файлы плюс `release/inew-openbao-control-agent`, `manifest.json` и `SHA256SUMS`.
3. Версия Release должна совпадать с `version` в manifest.
4. SHA-256 архива публикуется в описании GitHub Release по независимому каналу формирования комплекта.
5. До публикации проверяются разрешённый состав, отсутствие ссылок, секретов и внутренних путей.
6. Версия 1 является офлайн-релизом без цифровой подписи и автоматического обновления.
